# ループ判定基準 (criteria)

題材: **仕様と実装の同期 — センサーIDの全角数字受理バグの修正**(docs/spec.md 準拠)

## 完了条件(検証可能なゴール)

以下を**すべて**満たすこと:

1. `python3 -m unittest discover -s tests` が終了コード 0(全テストパス)
2. `ruff check src tests` が終了コード 0(lint エラー 0)
3. 全角数字を含むセンサーID(例: `sensor０１`)が `InvalidSensorId` で弾かれることを
   検証するリグレッションテストが tests/ に存在し、修正前の実装ではそのテストが落ちる
   (=欠陥を検出できるテストである)こと
4. Checker の High 指摘が 0 件

## High / Medium / Low の定義

- **High**(1件でも差し戻し): 検証ゲート不合格。または docs/spec.md と実装・テストの矛盾。
  または今回の題材の修正が実際には仕様を満たしていないことの実測証拠。
- **Medium**: 仕様違反ではないが放置すべきでない問題。欠陥を検出できない見せかけのテスト、
  題材スコープ外の変更の混入、仕様に記述のない曖昧な境界ケースの発見など。→ backlog へ。
- **Low**: 可読性・命名・コメント等の改善余地。差し戻し理由にしない。→ backlog へ。

## エラーの性質判定(エラー=バグではない)

| 観測 | 分類 | 扱い |
|---|---|---|
| 不正形式ID(`probe01`, `sensor1`, `sensorAB`, 全角数字入り)で `InvalidSensorId` | 想定内の異常系 | 対応不要(仕様どおり) |
| 温度が非数値で `ValueError` | 想定内の異常系 | 対応不要(仕様どおり) |
| フィールド数≠3 で `ValueError` | 想定内の異常系 | 対応不要(仕様どおり) |
| 仕様が「弾け」と定める入力(例: 全角数字ID)が**受理される** | 本当のバグ | 修正対象 |
| 仕様が受理を定める入力(ASCII数字2桁)が弾かれる | 本当のバグ | 修正対象 |
| 仕様に記述がなく判断できない挙動 | 判断保留 | 修正せず STATE.md 未解決事項へ |

## 人間確認マトリックス(可逆性 × 影響範囲)

| 可逆性 | 影響範囲 | 扱い |
|---|---|---|
| 戻せる(git で revert 可) | 狭い(このリポジトリ内のコード/テスト/docs) | **自動採用**し事後サマリで報告 |
| 戻せる | 広い(公開API仕様の変更、依存追加) | 実行前に同期承認 |
| 戻せない(push、リリース、データ削除、外部送信) | 問わず | 実行前に同期承認(初回題材では扱わない) |

本題材の修正(ローカルのコード+テスト変更、未コミット)は「戻せる×狭い」なので自動採用。
git commit / push はこのマトリックスとは別に、ユーザーの明示指示があるまで行わない。

## 停止条件(多層)

- 反復 **5回** 上限
- **2回連続**で改善なし。「改善なし」= ゲート不合格数も High 指摘数も減らないイテレーション
  (機械判定できる定義。典型例: 同じテストが同じ理由で落ち続ける)
- ツール連続失敗(同一コマンドが環境要因で3回連続失敗)
- いずれかで status を `requires human review` にして停止し、要約を STATE.md に残す
- 予算: 無人実行は1セッション内の /loop 呼び出しに限る(Automations 未有効化のため自然に上限)

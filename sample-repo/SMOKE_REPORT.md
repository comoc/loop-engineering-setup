# loop-engineering-setup スキル スモークテスト報告

- 実施日: 2026-08-29
- 対象リポジトリ: sample-repo(templog — 温度ログ行パーサ)
- 実行モード: **無人実行**(ユーザー不在)。承認が必要な箇所は推奨デフォルトを採用し、その旨を各成果物に明記した。Automations は雛形提示のみで未有効化。Phase 4 のサブエージェントは起動せず、生成した loop-maker.md / loop-checker.md の指示を報告者自身が役割になりきって順に実行した(Checker フェーズでは編集ツール不使用を厳守)。

## 1. 各 Phase で実際に行ったこと

### Phase 1 — 診断
- README.md / docs/spec.md / src / tests を精読。
- 検証ゲートを実際に実行して確認: `python3 -m unittest discover -s tests` → 4件パス(EXIT=0)、`ruff check src tests` → エラー0(EXIT=0、ruff 0.15.11 環境に存在。設定ファイルはなし)。mypy / black / flake8 も環境に存在するが未採用。
- git 状態確認: main ブランチ、クリーン(`__pycache__` のみ untracked)、worktree 利用可。
- 既存 Claude Code 資産: CLAUDE.md / .claude/ ともに**なし**。
- 仕様と実装の突き合わせで乖離を1件発見・実測確認: spec は「センサーIDは sensor + **半角(ASCII)数字ちょうど2桁**、全角数字は `InvalidSensorId` で弾く」と定めるが、実装の `digits.isdigit()` は全角数字にも True を返すため **`sensor０１` が受理される**(実測で確認。本当のバグ)。既存テストはこのケース未カバー。

### Phase 2 — 設計

## 4. 試運転の結果(1イテレーション)

**修正対象**: `validate_sensor_id` が全角数字ID(`sensor０１`)を受理する仕様違反(docs/spec.md 違反)。

- **Maker 役**(loop-maker.md の手順に従い実行):
  - Step 1 エラー性質判定: 全角数字受理=本当のバグ(spec「全角数字…を弾くこと」に違反)。既存の `InvalidSensorId`/`ValueError` 送出は想定内の異常系で非対象、と判定。
  - Step 2 テストファースト: `tests/test_parser.py` に `test_fullwidth_digits_rejected` を追加 → **ゲートが実際に「落とせる」ことを実証**(unittest EXIT=1、`AssertionError: InvalidSensorId not raised`)。
  - 修正: `src/templog/parser.py` の判定を `digits.isdigit()` → `digits.isascii() and digits.isdigit()` に変更(+仕様参照コメント)。
  - Step 3 スコープ規律: 作業中に「温度フィールドは全角数字が `float()` に通る」事実を発見したが仕様に記述がないため**修正せず** backlog/未解決へ記録。テスト網羅不足(仕様記載の異常系テストなし)も backlog へ。
  - Step 4 ローカルゲート: unittest EXIT=0(5件)/ ruff EXIT=0。「完了」は名乗らず Checker へ。
- **ゲート実行**(/loop 手順のオーケストレータとして): unittest EXIT=0、ruff EXIT=0 を記録。
- **Checker 役**(loop-checker.md の手順。**編集ツール・書込系 Bash 不使用を厳守**):
  - ゲートを**自分で再実行**: unittest EXIT=0(5件)/ ruff EXIT=0。
  - 仕様突き合わせ実測: `sensor０１`(全角)・`sensor٠١`(Arabic-Indic)・`sensor¹²`(上付き)・`sensor1`・`sensor123`・`probe01` の拒否、`sensor01/00/99` の受理を確認。
  - テストの欠陥検出力: 旧ロジック(`len==2 and isdigit()`)が `０１` を True にすることをメモリ上で実測し、追加テストが旧実装で落ちるものであることを確認。
  - スコープ確認: `git diff --stat` で変更が parser.py(+4/-1)/ test_parser.py(+5)の2ファイルのみ。
  - **判定: PASS(High 0 / Medium 2 / Low 0)**。Medium: ①温度の全角数字受理は仕様未規定(仕様確認要)②仕様記載の異常系テスト未整備。→ いずれも backlog へ。
- **STATE.md の更新**: status を `running` → **`done`** に更新。試行履歴#1(Maker 要約・ゲート生結果・Checker 判定)、採用判定(戻せる×狭い→自動採用。commit はユーザー指示待ち)、未解決事項1件、backlog 2件を記録。
- **停止・エスカレーション判定**: status=done 後の /loop 再実行が「何もせず終了」となるガードを机上確認。**反復上限・無進展検出の実発火は未確認**(1イテレーションで完了したため。§6-6 参照 — 改訂版スキルではドライラン手順として明文化済み)。

## 5. 運用ガイド(Phase 5)

- **回し方**: まず `/loop` を都度実行(1回=1イテレーション)。安定したら `docs/loop/automations.sample.md` の雛形を検討し、**L1(報告のみ)→ L2(承認付き修正)→ L3(無人実行)** の順で自律度を上げる。有効化は必ずユーザー自身が行う。
- **コストガード**: 反復5回上限・無進展2回検出・連続失敗停止を criteria.md のまま保つ。緩めるのは実測してから。Automations 未有効化のため現状の予算上限は「手動 /loop の回数」で自然に守られる。
- **残る責任**: 検証の責任は人間に残る。ループが生んだ diff(今回: parser.py / test_parser.py)を読むこと。STATE.md の backlog と未解決事項(温度の全角数字の扱い)は人間の判断待ち。理解負債と認知投降は静かに蓄積する。
- **並列化**: 複数ループを回す前に `git worktree` で作業空間を隔離する(現構成は worktree 利用可)。

## 6. 【最重要】スキル(SKILL.md)への率直なフィードバック — 曖昧・矛盾・不足・迷った点と改善提案

(スキル初版に対する指摘。多くはその後のスキル改訂で反映済み)

1. **診断レポートの評価(A〜F)の基準が未定義**。例示表があるだけで、何をもって B/C/F とするかのルーブリックがない。実行者の裁量で評点がぶれ、再現性がない。「動作確認済ゲートあり=B、設定恒久化+CI で A」のような段階定義を書くべき。→ **反映済み(評価の目安を追記)**
2. **「承認を得てから生成に進む」(Phase 2)と無人実行の規定が題材選定にしか及んでいない**。無人時の規定は「最小の題材を選び前提を明記」のみで、設計書全体(停止条件・人間確認マトリックス等)の承認をどう代替するかが未規定。今回は「未承認・推奨デフォルト採用を明記+同期承認が必要な操作は一切行わない」と自前で補った。この代替手順をスキルに明文化すべき。→ **反映済み(無人実行時の規定を全Phase共通化)**
3. **診断レポートと設計書の保存先が未指定**。「提示する」とだけあり、ファイルとして残すのか会話に流すだけかが不明。スキル自身の原則2「状態はコンテキストではなくディスクに」に照らすと docs/loop/ に保存すべきに思えるが、Phase 3 の生成物リストに含まれていない。→ **反映済み(REPORT.md / DESIGN.md として保存)**
4. **Automations「雛形を提示」の提示方法が曖昧**。ファイルとして置く場合の置き場所規定がなく、`.github/workflows/` に置くと push した時点で有効化されてしまう。「実行可能な場所には置かず docs/ 配下に .sample として置く」等の安全規定を明記すべき(今回は自主判断で docs/loop/automations.sample.md とした)。→ **反映済み**
5. **Checker の「Bash(検証コマンド再実行用)に限定」が性善説**。Bash が使えれば sed -i・リダイレクト・git 操作で事実上編集できるため、tools 宣言だけでは「修正を物理的に禁止」にならない。エージェント定義のプロンプトに「書込を伴う Bash 禁止」を書けという指示、さらに hooks / permission 設定による機械的強制への言及が欲しい(今回は自主的にプロンプトへ明記)。→ **反映済み**
6. **Phase 4 の確認事項「停止・エスカレーション判定が機能するか」が「1イテレーションだけ実行」と両立しない**。反復上限や無進展検出は複数イテレーション回さないと実発火しない。今回は status=done ガードの机上確認止まり。「STATE.md を人工的に上限直前の状態にして /loop が停止するかをドライランで確認する」等の手順を Phase 4 に追加すべき。→ **反映済み(ドライラン手順を追加)**
7. **「サブエージェント呼び出しが必要な構成なら tools に Task(Agent) を忘れない」の対象ファイルが不明瞭**(Phase 3-2、Maker の項に記載)。標準構成では Task を使うのは /loop(メインセッション)であり、Maker/Checker の agents 側には不要のはず。→ **反映済み(/loop の項に移動し明確化)**
8. **STATE.md の更新責務が未規定**。Checker は Write を持たないため判定を自分で STATE.md に書けない。誰が転記するのか(今回は /loop のオーケストレータ責務と定義)がスキルに書かれておらず、/loop の設計時に迷う。→ **反映済み(オーケストレータの責務と明記)**
9. **停止条件「2回連続で改善なし」の「改善」が未定義**。落ちるテスト数か、同一エラーの再発か、機械判定するためのメトリクス定義がない。今回は「同じテストが同じ理由で落ち続ける」と自前で具体化した。推奨定義を示すべき。→ **反映済み(ゲート不合格数・High指摘数で定義)**
10. **「CLAUDE.md 追記」— ファイルが存在しない場合の扱いが未記載**。「既存内容は壊さない」とあるのみ。新規作成でよいと常識で判断したが、一言「なければ新規作成」と書くだけで迷いが消える。→ **反映済み**
11. **Connectors の診断方法が未指定**。リポジトリ側の設定(.mcp.json)を見るのか、実行環境側の接続を見るのかで評価が変わる。→ **反映済み(両方を見ると明記)**
12. **無人実行時の「題材2〜3件提案してユーザーと決める」の扱いが不明**。候補列挙をスキップしてよいのか、記録として残すのか未規定(今回は設計書に候補比較を残した)。
13. **軽微/提案**: (a) 診断レポート例の「検証ゲートを1行目に置く」指定は良いが、表の凡例(評価列の意味)も例に含めると親切。(b) Phase 4 で「意図的に失敗を作って確認してよい」とあるのは有効だった — テストファースト(先に RED を確認)を推奨手順として本文に昇格させると、ゲートの欠陥検出力の実証が毎回担保される。→ **(b)は反映済み** (c) 生成物に「/loop の実行前提(Task ツールが使える環境)」のような前提条件節があると、他環境への持ち出し時に安全。

**総評**: スキルの骨格(診断→設計→生成→試運転→運用、Maker/Checker 分離、状態のディスク永続化、停止条件の多層化)は一貫しており、そのまま従って実際にバグ1件を仕様根拠付き・独立検証付きで修正完了できた。改善の余地は主に「無人実行時の承認代替」「提示物の保存先」「Checker の Bash 抜け穴」「停止条件の実発火テスト手順」の4点に集約される(いずれも改訂版スキルに反映済み)。
